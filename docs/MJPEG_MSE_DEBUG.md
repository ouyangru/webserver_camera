# MJPEG 检测与 FLV 播放排查（2026-11-03）

- 旧 MJPEG 通过原生 img 播放，取不到逐张 JPEG 的 multipart 时间戳。检测开关此前强制切换 FLV，现已取消。
- 采集发布 JPEG 时保存与推理相同的 DQBUF 单调时间。multipart 部件新增 X-Capture-Mono-Us；网页逐段解码并在同一画面上叠加匹配结果。浏览器已验证显示帧与结果时间戳相等。检测开启时，为等待推理和轮询会增加有限的 MJPEG 显示缓冲；关闭时不额外等待。原始 /mjpeg 流仍是未画框的 JPEG。
- 浏览器旧日志显示 SourceBuffer Error，随后因 HTMLMediaElement.error 已设置而反复 appendBuffer 失败。第一次错误的直接触发原因未保存，不能断言是码流损坏或内存。现场原流持续 35 秒 ffmpeg 解码通过。新版首次报错即停止追加并重连，记录底层媒体错误码和消息，并限制保留的回看缓冲。
- 同一张倒置的现场图片对照：270° 无结果，180° 检出两个瓶子，最高置信度 0.823。板端 /etc/webserver_cv.conf 已设 180°，仅改变推理输入方向，框仍映射回原画面。相机转动后需重新校准。
- 无框可能是该帧未运行推理、结果还未到，或模型确实没有检测到目标。多类 YOLOv5s 在板上约 4fps，严格同步下很多视频帧天然无结果。旧框保持最多 250ms，不能替代跟踪或提高召回率。
- 模型沿用厂商预转换的 YOLOv5s 640×640，实测为 U8 量化输入输出，未自行剪枝、蒸馏或重新量化。硬件推理和限频不算模型压缩。下一步可对更小的网络与输入尺寸重做板端转换，对比同一现场测试集的召回率、推理耗时与内存。
- MJPEG 软件 JPEG 同时开启时，现场单帧约 73ms，采集约 11fps；FLV 单独约 20fps。该性能瓶颈与本轮检测框同步修复是两件事。
