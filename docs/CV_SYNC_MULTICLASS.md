# 检测同步、直播开关与多类别扩展

日期：2026-11-02。本文件记录本轮实现理由与验证，未写“通过”的部分不能视为已验收。

## 要解决的问题

旧版 cv.html 显示最新检测结果，而 FLV 播放器还在播放缓冲中的旧帧，因此框会先于对应画面出现。检测结果已有板端时间戳，但视频没有把这一时间轴交给浏览器，只有时间戳字段并不足以实现同步。

## 实现方案

1. 同一次 DQBUF 的单调时间戳同时传给 NV12 推理发布与 Cedar 编码，避免采用彼此不同的“编码开始”和“推理开始”时间。
2. H.264 NAL/组帧/FLV Packet 保留采集时间；每个客户端以首个可解码关键帧为零点重写 FLV 时间戳，首帧从0开始，与 flv.js 无音频、无B帧的播放时间轴对应。
3. 每个视频 FLV tag 前插入 AMF0 `onFrameClock` 脚本事件，包含该帧 capture_us 与客户端相对 pts_ms；与该视频 tag 在同一发送队列包内，不能把部分已发送tag截断。
4. 浏览器用 requestVideoFrameCallback 的 mediaTime 匹配视频帧时钟，再从有界历史结果中选择相同 capture_us 的检测结果。无匹配则不画框，不直接显示最新结果。
5. 默认严格同帧；可选“平滑保持旧框”允许沿用过去250ms的结果，永远不使用未来帧的结果。这是旧结果保持，不是该帧真实推理或运动跟踪。慢模型在严格模式下只有推理过的帧有框，不能声称每帧都有检测。

当前为单路 Baseline H.264、无音频无B帧。以后加入B帧、音频、其他转封装器时，需要重新验证PTS重排和播放时间轴映射，不能直接照搬。

## 产品行为

检测功能在首页直播播放器上叠加，提供人形/物品两个开关；默认都关闭，页面默认使用FLV。旧 cv.html 跳转首页。
两开关均关闭时不发布NV12推理帧，worker释放已加载的NPU模型；直播继续。
仅人形开启时运行轻量人形模型，尝试跟随约20fps采集。物品开启时使用供应商YOLOv5s COCO80模型；同时开启人形时用同一次YOLO推理同时返回person与其他类别，避免重复跑两套网络。
“物品”仅覆盖COCO定义的类别，不代表任意物体/开放词汇检测。关闭人形但开启物品时过滤person结果。

控制接口为 POST /api/detection/off、/person、/objects、/all。状态含mode位掩码：1人、2其他类别、3全部；GET控制请求不应生效。结果历史 GET /api/detection/results，最多80条；接口不返回图像或凭据。
开关控制板子的共享推理服务，不是每个浏览器各起一个NPU。新连接通过状态轮询看到当前开关；不同浏览器改开关会相互可见。

## 多类别模型与适配

来源为百问网 AICT 的 YOLOv5 部署资源包，模型、归档校验值与来源记录在 vendor/100ask-cv/yolo/SOURCE.md。
沿用已经匹配驱动的VIPLite 1.8.0，通过网络API查询输入输出，按实际张量数据格式/量化参数解码，不用人形专用后处理来解析YOLO。
供应商示例输入是平面BGR，模型输入640×640；实现NV12颜色转换、等比缩放/补边、安装方向校正、量化输出反算、YOLOv5 anchors与同类别NMS，再映射回原图。
运行时需要先prepare network，再set input/output。首次实板测试暴露了顺序错误，已按供应商示例修正；不能把第一次失败当作模型不兼容。

## 实测与使用限制

人形模型已改为尽量跟随每个采集帧：约19.9fps推理，视频约20fps；浏览器严格模式可连续得到同帧结果。新帧发布上限25fps，慢推理仍读取最新帧，不无限排队。
YOLOv5s COCO80在本板实际约4.2fps，单次NPU约175ms、NV12到640×640平面BGR预处理约50ms，后处理约5～8ms；联合检测时视频仍约20fps。它比轻量人形模型消耗更多资源，不能用旧版人形12ms数据代表多类别性能。
YOLO的请求heap为80MiB，RSS约6.2MiB，RSS不包括全部NPU内存。关闭后观察到驱动执行aw_vip_mem_free、ion_free及vipcore un-init；不要只凭RSS估算释放量。
首次离线输出曾把模型加载时间计入单帧后处理，已修正计时边界。首次部署更新曾因ADB目录嵌套而运行旧文件，改为逐文件上传并核对校验值；最终测试基于新文件。

同帧检测不意味着零延迟：视频解码缓冲仍存在。慢模型严格模式会有无框帧；可选保持模式只沿用过去结果，最多250ms，运动时可能有滞后。没有实现插值或目标跟踪，不把保持结果称为该帧重新推理。
控制冒烟脚本为tests/cv_control_smoke.py，会改变板端共享开关，并在结束时恢复原mode。性能计数每2秒更新，关闭测试需要等待采样刷新后再比较，避免把旧快照误认为仍在发布。

历史测试数据仍在 V853_CV_VALIDATION.md，本轮功能变更后的结果将在此补充，不用旧版数据冒充本轮验证。

## 本轮交付与操作

入口：http://127.0.0.1:18080/index.html 。勾选“人形检测”或“物品检测”，可同时勾选；都不勾选就是普通直播。旧cv.html只是兼容跳转，不再单独维护一套播放器。
默认严格同帧，平滑旧框保持默认不勾选。人形模型可接近视频帧率，多类别模型约4fps，所以严格模式下物品框可能间歇显示；不需要逐帧严格显示时再启用旧框保持。
保持后台独立worker用于隔离NPU故障，界面、控制、帧数据和结果接口均由流媒体应用统一对外提供。没有要求用户手动另开模型程序。

实板测试原始记录保存在本地outputs/yolo-bus-board-test.txt、outputs/cv-control-final-report.json；前端确定性回归为tests/detection_overlay_test.js，网络和模式回归为tests/cv_control_smoke.py，发送/AMF回归扩展在tests/send_queue_test.cpp。
最终Tina包同时包含person模型、yolov5_model.nb、webserver_cv、detection.js、首页及开机脚本。当前为工作区修改并已ADB部署，未提交或推送；未刷入新完整固件镜像。

后续优化重点是YOLO模型的NPU耗时与颜色缩放成本、低推理帧率下的目标跟踪、长期运行与场景精度。不能把80个训练类别理解成任意物体均能识别。
