# V853 低延迟与 CV 部署优化记录

## 基线与范围

已工作的链路是 GC2053 → VIN 多平面 NV12 → ISP → Cedar H.264 → HTTP-FLV → flv.js。
此前现场短时采样：640×480 / 15 fps，程序 RSS 约 263 MiB，CPU 约 90%，系统可用内存约 195 MiB。
这些是旧版本的基线，不代表优化后的数据。

## 修复和取舍

1. **连接内存**：65536 个对象的读写缓冲单独就预占约 192 MiB。改为 1024 个指针槽，连接到来时创建对象，最多 32 个活动连接；工作线程改为 2 个、任务队列上限 64。
   槽位在断开后保留复用到进程退出，不立即 delete。原因是广播线程和线程池目前仍持有原始指针；立即回收会引入悬空指针。
   这控制了内存上限，但没有解决旧架构中同一 fd 关闭/复用与旧任务重叠的全部并发问题。更彻底的方案是共享所有权及连接代次校验。
2. **JPEG 按需执行**：保留一次预热帧，此后只有 MJPEG 客户端存在时才软件编码 JPEG。仅看 FLV 时跳过该工作。NV12 临时帧改为循环外分配复用。
3. **重复限速**：摄像头实时源已经按采集速率供给，FLV 线程再次每帧 sleep 会逐渐积压。仅文件回放保留主动 sleep；实时源采用单调时间生成时间戳。
4. **完整帧边界**：Cedar 已返回完整帧，却由通用 NAL 组帧器等下一帧才能确认边界。实时源帧尾追加 AUD，让组帧器立即 flush。新增 source_mono_us 标记编码输入时间；它不是传感器曝光时间。
5. **有界队列**：编码总线限制 4 帧/250ms；超限丢弃未发送的完整编码帧并等待 IDR。客户端发送队列限制 12 包/512KiB/500ms。超限关闭慢连接，由播放器重新获取 HTTP/FLV 配置及 IDR。
   不清空已部分发送的 FLV tag；否则客户端字节流会损坏。以上阈值是初始策略，需根据真实网络抖动和画面大小继续调优，不是端到端延迟承诺。
6. **浏览器**：显示缓冲领先量。初版在积压 >0.8s 时跳至末端前 0.2s；实测正常播放本身约有0.8s缓冲，频繁 seek 会引入停顿，因此改成积压 >1.5s 才跳至末端前0.6s，并设置5秒冷却。策略可关闭。flv.js 随页面本地提供，使局域网播放不依赖外网 CDN。网页事件日志只保留最近 100 条。

## 可观测性

`/api/status` 增加 `performance`。后台每 2 秒采样 CPU、RSS、MemAvailable、实际编码 fps，并汇总阶段耗时及队列状态。
阶段 avg/p95/max 来自最近最多 256 个样本；不是每个采样周期清零。counters 是进程累计值。
CPU 百分比按进程 CPU 时间/墙钟时间计算，100% 代表占满一个核。

- capture_wait：等待并取到 V4L2 帧的耗时；capture_interval：相邻取帧间隔。
- capture_driver_age：仅驱动声明 MONOTONIC 且提供有效时间戳时记录。
- nv12_copy、encode、jpeg、capture_buffer_hold：CPU 拷贝、编码调用、JPEG 和持有驱动缓冲区耗时。
- encoder_queue_wait、encoder_input_to_mux：编码队列等待、编码输入到 FLV 封装前的耗时。
- send_syscall、send_queue_residence：系统调用耗时、应用队列驻留时间。
- queues：当前编码帧数、所有客户端待发送包/字节总数、最旧待发送数据的帧龄。

应用队列不包含内核 TCP、ADB、网卡和浏览器的全部缓冲。RSS 不完整涵盖 DMA/ION/NPU 预留内存。
端到端延迟需拍摄同一时钟/物理事件验证，跨设备时间戳不能未经同步直接相减。

启动脚本设置 `WEBSERVER_LOG_LEVEL=INFO` 与 `WEBSERVER_LOG_FILE=/tmp/webserver_camera.log`。
结构化日志约每 2 秒一条性能汇总；文件达到 1 MiB 时轮换到 `.1`，最多保留两份。TRACE 仅用于短期定位，不建议长期启用。

## 切换局域网

服务器已经绑定 `INADDR_ANY`，无需修改网页或重新编译。
板子获得局域网 IP 后，电脑访问 `http://板子IP:10000/index.html`；ADB 的 18080 转发可以同时保留。
板子和电脑需要可互通，注意访客 Wi-Fi/AP 隔离。先用有线网络验证能减少 Wi-Fi 抖动的干扰。
若 `ifconfig -a` 和 `/sys/class/net` 只有 lo，应先处理驱动、设备树、电源或硬件枚举；配置 SSID 本身不会创建网卡。
不要在日志、Git 提交或状态接口中记录 Wi-Fi 密码。

## 后续 CV 模型

视频编码与推理分支解耦：采集 → 编码推流；另一路最新帧 → 缩放/预处理 → NPU → 后处理。
推理队列只保留 1～2 帧，模型初始推理率 3～5fps，不阻塞 15fps 视频链路。
需要计时预处理/推理/后处理并测量模型加载后及推理峰值内存；不能仅用模型文件大小或 1TOPS 标称值估算。
检测结果带帧标识/时间戳；若必须在编码前叠加结果，要明确等待结果带来的延迟代价。

## 验证状态

已完成主机媒体组帧/封装测试、短写/EAGAIN/IDR/背压回归和 100 次请求的 HTTP/FLV/本地播放器冒烟测试。
V853 独立交叉编译、Tina 包构建、根文件系统构建与完整镜像打包均已通过。最后的小修正需重新生成最终产物。

板端仅 FLV、无 MJPEG 观众的初步对比：旧版 CPU 短时约 82%～92%、RSS 269512KB；优化版 CPU 约7%～11%、RSS 5948～6012KB、MemAvailable 约460MB（以KB值为准）。
实际取帧间隔约50.7ms，编码约19.5～20fps；驱动没有按请求的15fps供帧。因此状态中原有 fps 字段是配置值，`performance.encoded_fps` 才是采样吞吐率。
编码 P95 约4.8～7.3ms，编码输入到封装约4.7～7.2ms，取样时编码队列为0。不是完整摄像头到屏幕延迟。
原始 H.264 150帧、HTTP-FLV HTTP200及解码均通过。

浏览器验证发现并修正：性能渲染代码应放在状态轮询回调；每个 IDR 重复的同内容 SPS/PPS 不应触发重新广播 AVC 配置。
还增加采集初始化退出后的1秒重试，防止快速重启服务时临时设备占用导致永久没有采集。

联网排查：XR829 驱动能检测到 SDIO 卡并完成 bootloader，随后 `Timeout waiting for FIFO / can't download firmware (-110)`，最终移除 SDIO 卡。
构建已启用 `CONFIG_XR829_USE_40M_SDD=y` 与 `kmod-net-xr829-40M`，因此不能简单认定只是没开40MHz选项或没填SSID。
网卡未恢复前，局域网访问与局域网端到端延迟尚未验证。已核对的官方参考：https://docs.aw-ol.com/v853/hard/hard_2boraduse/ 和 https://docs.aw-ol.com/v853/en/soft/tina_wifi/ 。

用户照片确认核心板丝印为 `AICT-V853 BTB 0.5mmx60Pinx3`，底板可见 V1.1。百问网 AICT 文档确认套件使用 XR829：https://vision.100ask.net/docs/V853/BoardIntroduction/ 。
进一步核对 SDK 发现，100ask 目标使用默认 SDD（SHA256 a504e351…），vision 目标和当前板上使用40M SDD（7bc630f3…），Wi-Fi 主固件相同。
